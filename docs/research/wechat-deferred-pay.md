# 微信「先用后付 / 先享后付」通知可行性调研

> 2026-10-29 · 目的：判断「先用后付」能不能靠通知稳定自动记账（对应 `docs/APP-DESIGN.md` §4.4）。
> 结论先行：**能识别一部分，但不能承诺覆盖**。只在通知文本里同时出现「先享后付 / 先用后付 / 支付分」和金额时记账；不满足就按普通微信支付处理，纯「扣款成功」而无关键字一律不猜（返回 `Unparsed`，进「没认出」日志）。

## 1. 这项服务到底是什么

财付通《微信支付分先享后付用户服务协议》（2026-04-08 修订，05-08 生效）第 1.1 条原文要点：

> 当符合条件并开通本服务的用户在支持先享后付服务的商家处购买商品或服务时，可选择享受先享后付的专享服务（即下单时无需付款，收到商品或完成服务后自动付款）；在用户收到商品或服务完成后（包括主动确认收到商品/服务完成或根据系统规则自动确认收到商品/服务完成后），本公司将根据为用户提供商品或服务的商家发出该笔交易的扣款指令，从用户的微信支付账户、与用户的微信支付账户相关联的银行账户或用户的其他可用扣款渠道扣划相应款项至商家的指定账户。

关键信息：

| 项 | 内容 | 来源 |
|---|---|---|
| 触发扣款时机 | 收货/服务完成后，用户主动确认或系统自动确认 | 协议 1.1 |
| 扣款渠道 | 零钱、绑定银行卡、其他可用扣款渠道 | 协议 1.1、5.2 |
| 缺额处理 | 「有权通过包括但不限于短信、**微信消息**等方式通知你补缴欠款」 | 协议 3.3 |
| 关闭路径 | 我-服务-钱包-支付分-我的服务 | 协议 2.3 |
| 名称稳定性 | 「在不同的运用场景下，本服务的名称可能发生变化」 | 协议 1.1 |

- 协议：https://posts.tenpay.com/posts/7a85e5d469d60d43002fac9c68a251a0.html
- 微信支付分产品介绍：https://pay.weixin.qq.com/doc/v3/partner/4012586132
- 支付分服务端「先享模式」参数（`ESTIMATE_ORDER_COST` 等）见 https://pay.wechatpay.cn/doc/v3/partner/4012586134

## 2. 通知从哪来、长什么样

### 2.1 通道层面区不出来

本机（vivo V2405A，微信 8.x）`dumpsys notification --noredact` 里 `com.tencent.mm` 的全部通知 channel：

| channel id | 名称 |
|---|---|
| `message_channel_new_id` | 新消息通知 |
| `reminder_channel_id` | 其他通知 |
| `voip_norify_channel_silent*` | 音视频通话邀请通知 |

**没有支付分 / 先享后付专属 channel**。微信支付、微信支付分、普通聊天消息都走 `message_channel_new_id`，所以「按 channel 判定是不是扣款」这条路直接排除，只能看文本。

支付宝侧 channel 有 `ACCOUNT`「资金交易与账户安全」、`ORDER`「服务履约」、`miniAppPay`「小程序支付」等，粒度更细，但同样不能单独作为交易判据。

### 2.2 文案由服务端下发，客户端枚举不到

- 扫本机微信 APK（285 MB，base.apk）：`resources.arsc`、全部 `classes*.dex`、`assets/` 里**没有**「先享后付」这个字符串；「先用后付」只出现在小程序基础库 `assets/wxa_library_legacy/WAWebview.js` 里，且是商品标签（`PAY_AFTER_USE: 先用后付`），不是通知文案。
- 微信支付类通知是「微信支付」服务号的公众号消息，正文由服务端拼装。客户端 APK 里能查到的只有通用词：`支付成功`、`付款成功`、`支付总金额`、`收款方: %s`、`[转账] 已收款`。
- 协议明写「服务名称可能发生变化」。⇒ **不能把某一版文案当成契约**，只能按关键字 + 金额的保守规则匹配。

### 2.3 已知风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 漏识别 | 文案换词、只说「扣款成功 ¥15.00」不带「先享后付」 | 退化成普通微信支付规则；仍识别不了就进「没认出」日志，由用户手动补 |
| 误识别 | 「支付分」营销推送、开通成功、额度提示 | 打开 `adKeywords` 营销拦截 + 要求出现金额、且方向为支出 |
| 双记账 | 先享后付扣款可能同时有「订单已确认」和「扣款成功」两条 | 沿用 `CaptureProcessor` 2 分钟内同金额同方向去重 |
| 语义不清 | 扣款时点是「服务完成后」，账目时间会晚于实际消费 | 账目时间用通知时间；不额外推算，避免编造 |

## 3. 落到 parser 的策略

规则（`PaymentNotificationParser`，微信包）：

```kotlin
// 关键字 gate：必须出现「先享后付 / 先用后付 / 支付分」，且带金额
rule("wechat.deferred.keyword", WX, """(?:先享后付|先用后付|支付分)[^。\n]{0,24}?{YEN}{AMT}""")
// 扣款叙述形：「先享后付订单扣款成功，金额 ¥15.00」
rule("wechat.deferred.deduct", WX, """(?:先享后付|先用后付|支付分)[^。\n]{0,24}(?:扣款|扣费|付款)[^¥￥\d]{0,10}{YEN}{AMT}""")
```

- 方向固定 `OUT`（从用户账户扣款）。
- 商户名走通用 `merchantExtractors`（`收款方：`、`商户：`）；抓不到就留空，落库时按 `微信支付` 兜底。
- **不新增**「只有『扣款成功』+ 金额」这类宽规则：微信里「扣款」还会出现在亲属卡、自动续费、免密支付等场景，没有关键字就分不清是哪种，属于「猜」，违反 §4.4 的「识别不了的不猜」。
